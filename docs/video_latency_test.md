# 图传回传延迟时间码测试

## 测量边界

本工具使用同一台电脑的`perf_counter_ns()`单调时钟，显示带本次会话ID、递增序号、生成时间戳和CRC的二维码。机载相机拍摄源窗口，图像经发射模块、深图接收机及USB回到电脑。程序识别回传码，并将它对应到本机保存的源提交时间。

主指标为：`捕获帧read返回时刻 - 源图像imshow提交前时刻`。

它包含源屏幕呈现、相机曝光/读出、图传、接收机转换、USB、驱动与取帧。它不包含二维码解码的运行时间，但二维码解码失败、处理线程未能看到更早的帧等因素会使首次有效样本偏晚。

这不是单独的接收机延迟，也不是精确的光子到PC延迟。代码不知道屏幕真正发光的时刻，不能随意扣除8ms、16.7ms或一个屏幕周期。要得到不含源显示的测量，需要额外光学/硬件时间基准或独立校准。

程序只使用OpenCV、NumPy和标准库，不加载YOLO，不打开COM口，不连接RTT，不发送任何机械臂或夹爪命令。测试设备与标记不属于机械臂正常控制系统。

## 操作

1. 接好相机、发射模块和深图USB接收机，选择匹配信道并获得稳定画面。
2. 关闭正在占用相机的YOLO、OBS、相机软件等程序。
3. 双击项目根目录`start_video_latency_test.bat`。默认视频源0、DirectShow、640×480。2026-10-22本机DirectShow枚举为0=`USB Video`（图传接收机，VID_534D/PID_0021）、1=`HD Webcam`（笔记本内置相机）；重插或更换电脑后编号可能变化，应重新核对。
4. 会出现SOURCE时间码窗口与RECEIVED回传预览。让相机只拍SOURCE窗口，不要拍到RECEIVED窗口或递归反馈画面。
5. 保留二维码周围白边，让它在回传画面中尽量正对、清晰，占据足够面积。建议二维码宽度至少250像素。出现PREVIEW和毫秒数后再开始。
6. 点击窗口，按空格开始。默认预热2秒，再记录45秒，每秒更新8个时间码。
7. 到时自动保存退出。也可按Q、Esc或Ctrl+C提前结束，已有记录仍保留并标注未完整运行。

默认只预览，按空格才开始正式计时。要明确自动开始，可加`--auto-start`。

先确认机械臂处于你已选择的安全台架状态。本工具不会自动停止此前已经运行的机械臂程序，也不会改变执行器保持状态。

如果接收机枚举为其他编号，可在终端指定，例如：

```powershell
& 'D:\app\miniconda\envs\python312\python.exe' tools/measure_video_latency.py --source 1
```

避免在测量期间移动源窗口、缩放窗口或更改显示器刷新率、分辨率、接收机设置。先把桌面上的二维码以理想布局置于相机视野内。窗口文字为英文，操作说明以本文为准。

## 文件与统计

每次运行新建`outputs/video_latency/<时间_会话ID>/`，不覆盖之前的数据。

- `summary.json`：中位数、P95、平均、最小和最大，设备/后端/请求参数、样本数量、测量边界和质量提醒。
- `samples.csv`：每个唯一时间码的首次有效回传样本，可直接用Excel打开。
- `source_events.csv`：源窗口各次提交时间和完整时间码，可复核样本对应关系。
- `events.jsonl`：开始、样本及异常事件。
- 最多3张`received_*.jpg`：保存最早的有效样本原始回传画面，在结束后写盘，不在测量中持续录制。

同一个时间码后续重复出现不会再次增加样本。外来会话、未发出的序号、CRC错误、时间倒置和超过上限的结果会拒绝。无有效样本时统计为null，不输出虚构的0ms。

样本少于30个会明确提示。即使样本充足，也需要检查是否拍到回传预览、曝光模糊或大量未解码。解码覆盖率不等于RF丢包率，尾部时间码可能尚未返回。

`summary.json`还保存实际源提交间隔，便于检查电脑解码负载是否使8Hz请求变慢。可用`--note "monitor 60Hz, camera PAL, receiver channel ..."`记录现场设置。它不会自动校准显示器延迟。

主指标`submit_to_capture_ms`不含二维码解码时间。`submit_to_decoder_finished_ms`包含程序拿到该帧后等待与解码的时间，可用于诊断。`source_preparation_ms`单独给出源二维码生成及绘制开销，不混入主指标。显示提交本身仍不是屏幕发光时间。

解码先尝试原画面，失败后尝试二值化和放大重试，样本中保存`decode_method`。重试耗时仍单独计入`qr_decode_ms`；较慢的解码可能造成应用漏过更早的帧，所以不能据此宣称接收机本体的精确延迟。

## 可调参数

```powershell
python tools/measure_video_latency.py --source 0 --seconds 60 --pattern-hz 5
python tools/measure_video_latency.py --source 0 --backend msmf
python tools/measure_video_latency.py --source 0 --fourcc MJPG --fps 50
```

默认不主动更改FPS、FourCC或曝光，避免自动替换当前设备模式。`--fps`和`--fourcc`是请求，驱动可能不支持或忽略；报告中记录其返回值和设备报告值，它们不能证明实际曝光帧率。缓冲区设置也可能不受支持。

默认最大接受延迟5000ms，若发生超上限拒绝，报告会指出分布被截断，应提高`--max-latency-ms`并重新测试。`--qr-size`可改变源二维码大小，默认512。

二维码更新不是越快越好。模拟视频、屏幕扫描和曝光跨越码变化时可能导致混合图像。解码困难时先改善对焦、角度、照明和二维码在画面中的大小，必要时降低到5Hz，不应把未解码样本当作低延迟或无延迟。

## 验证状态

可先运行不接相机、不打开窗口的检查：

```powershell
python tools/measure_video_latency.py --self-test
python -m unittest discover -s tests -p test_video_latency.py -v
```

检查包括二维码编码/解码、透视与JPEG回传近似、注入60ms延迟、重复码拒绝、会话/CRC校验、预热边界、异常时间戳及空结果。软件测试不等于实物图传测量，尚需按上面的光学布置完成现场一轮。

报告应表述为“软件显示提交至首次可解码回传帧的延迟”，并注明包含源屏幕。若要写“相机到PC延迟”或“接收机40–60ms已验证”，必须先补齐测试边界和独立物理测量。
